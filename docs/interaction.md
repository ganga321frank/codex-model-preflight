# 选档建议不再阻塞任务

## 判断与采用的方案

v0.1.0 要求新大任务建议后暂停，用户未回复时任务无法继续。v0.2.0 改为在进度消息里给出建议，同一轮立即按当前会话配置执行原任务。只有用户明确要求“先等我选档”才保留选档暂停。单独询问模型建议时只回答问题，不擅自做其他工作。

“按建议配置自动运行”与“按当前配置继续”是两件不同的事。这个包只包含指令和参考资料，不能操作模型选择器。当前会话可能覆盖配置文件默认值，因此降级方案准确的表述是“保留当前会话配置”，不能声称重置为系统默认配置、已经升档或已经降档。

## 为什么不写一分钟超时自动继续

OpenAI 的 [Build skills](https://learn.chatgpt.com/docs/build-skills) 将 Skill 描述为由 SKILL.md、可选脚本和参考资料组成的指令包。当前包没有计时器、回复监听、模型切换接口或后台服务。单纯写下“等待一分钟后继续”不能让一个已经结束的回复自行唤醒。

[Codex App Server](https://learn.chatgpt.com/docs/app-server) 提供由客户端发起的 turn/start，以及逐轮的 model、effort 等设置接口。由此判断，真正的计时后启动与切换应当做在宿主客户端或独立控制器里，不能声称当前纯指令包已有此能力。官方页面未给这个包提供一分钟响应超时机制；这里是结合包内实现作出的能力判断。

额外控制器至少要持久化任务与截止时间，辨别用户回复、取消、正在执行和已经结束的状态，防止重复启动，并只通过受支持的会话接口设置模型。它还需要单独测试重启、断线和截止时同时收到回复的情况。这超出本次轻量修复范围，不安装后台程序，也不创建定时自动化。

让模型每个任务先空等一分钟也会增加延迟，且不能解决结束回复后的唤醒问题。因此本次选择直接消除不必要的选择等待。若用户明确坚持实际计时或手动等待，则说明能力限制并尊重等待要求。

## 明确保留的边界

- “先等我选档”“先别做”仍应暂停，不能用超时覆盖。
- 必要权限、对外操作确认和关键资料缺失继续按实际规则处理，不能把一分钟沉默当成同意。
- 客户端已经终止、断线或取消的任务，不能靠这个 Skill 自动恢复。
- 默认当前配置可能高于或低于建议，不能承诺因此节省额度或获得建议模型的能力。

## 升级和验证

替换现有 Skill 后，还要检查项目或全局 AGENTS.md 中是否仍有旧的“选档后必须暂停”规则；更高层或明确的等待指令会继续影响行为。只更新选档段落，保留其他项目规则。参考 [触发规则](agents-snippet.md)。

在独立项目新开聊天，请它完成一个有明确交付物的小任务。期望看到简短建议后直接产生交付物，而不是只收到建议。在另一个新聊天中加入“先等我选档”，期望只建议并等待；回复“继续”后才执行。仅通过文字审查不能证明所有客户端都会稳定执行，实际验证结果记录在 [validation.md](validation.md)。
